## 1. What Reputation Stores

### 1.1 `reputation_entries` (durable, SQLite)

The only durable reputation store is the `reputation_entries` table, created by
migration version 4 (`create_reputation_entries`):

| Column | Type | Constraints | Description |
|---|---|---|---|
| `id` | `TEXT` | `PRIMARY KEY` | UUID generated by `randomUUID()` at insert time. |
| `reviewer_id` | `TEXT` | `NOT NULL REFERENCES users(id)` | User who submitted the rating. |
| `target_id` | `TEXT` | `NOT NULL REFERENCES users(id)` | User being rated. |
| `rating` | `INTEGER` | `NOT NULL CHECK (rating >= 1 AND rating <= 5)` | Rating value. |
| `comment` | `TEXT` | `CHECK (length(comment) <= 1000)` | Optional free-text review; `NULL` when omitted. |
| `context_id` | `TEXT` | `NOT NULL REFERENCES contracts(id)` | Contract the rating relates to. |
| `created_at` | `TEXT` | `NOT NULL` | ISO-8601 timestamp set at insert time. |

Additional schema objects: `UNIQUE(reviewer_id, target_id, context_id)` plus
indexes `idx_reputation_entries_target_id` and
`idx_reputation_entries_context_id`.

> **Source:** [`src/db/migrations.ts:102–130`](../src/db/migrations.ts#L102-L130),
> [`src/repositories/reputationRepository.ts:26–45`](../src/repositories/reputationRepository.ts#L26-L45)

There is **no** `updated_at`, no `deleted_at`, and no soft-delete column. The
repository exposes `create`, `findById`, `findByReviewerTargetContext`,
`findByTargetId`, `findByTargetIdPaginated`, `verifyContractParticipation`,
`count`, and `getDistinctTargetIdPage` — **no update and no delete method**.
Ratings are append-only by design: the `UNIQUE` constraint plus the absence of
mutation paths is what prevents a reviewer from rewriting or withdrawing a past
rating.

> **Source:** [`src/repositories/reputationRepository.ts:74–283`](../src/repositories/reputationRepository.ts#L74-L283)

### 1.2 Reputation profiles (derived, not persisted)

`ReputationProfile` (`score`, `weightedScore`, `totalRatings`, `reviews`,
`lastUpdated`, `scoreAlgorithm`) is **computed on every read** from the rows in
`reputation_entries` — it is not a stored table. `jobsCompleted` is a legacy
field hard-coded to `0`.

Because the profile is derived, deleting rows from `reputation_entries` is
sufficient to remove a user's reputation data from the authoritative store; no
separate aggregate row needs to be reconciled.

> **Source:** [`src/services/reputation.service.ts:489–534`](../src/services/reputation.service.ts#L489-L534) — `buildProfile()`

### 1.3 In-memory profile store

`reputationStore` is a module-level `Map<string, ReputationProfile>` singleton.
It is written **only** by the recompute queue processor, which persists each
freshly computed profile back into the map after a recompute pass.

```typescript
// src/queue/processors/reputation-recompute-processor.ts
const profile = ReputationService.getProfile(targetId);
reputationStore.set(profile);
```

Each stored profile carries the **full `reviews` array**, i.e. every reviewer ID
and every comment for that target.

> **Source:** [`src/models/reputation.store.ts`](../src/models/reputation.store.ts),
> [`src/queue/processors/reputation-recompute-processor.ts:88–101`](../src/queue/processors/reputation-recompute-processor.ts#L88-L101)

### 1.4 Recompute checkpoints

`reputationCheckpointStore` is an in-memory `Map<string, RecomputeCheckpoint>`
holding job-progress records so a failed recompute can resume:

| Field | Description |
|---|---|
| `jobId` | `recompute-<epoch-ms>` identifier. |
| `lastProcessedFreelancerId` | User ID of the last successfully processed target. |
| `totalProcessed` / `totalFreelancers` | Progress counters. |
| `startTime` / `lastUpdateTime` | ISO-8601 timestamps. |
| `status` | `running` \| `completed` \| `failed` \| `paused`. |
| `error` | Failure message when `status === 'failed'`. |

> **Source:** [`src/models/reputation-checkpoint.store.ts:7–16`](../src/models/reputation-checkpoint.store.ts#L7-L16)

### 1.5 Read cache

`GET /api/v1/reputation/:id` (unpaginated requests only) is served through
`reputationCache`, a bounded LRU cache of `ReputationProfile` objects keyed by
target user ID. Cached values include the full `reviews` array.

| Setting | Env var | Default |
|---|---|---|
| Entry lifetime | `REPUTATION_CACHE_TTL_MS` | `60000` (1 minute) |
| Capacity | `REPUTATION_CACHE_MAX_ENTRIES` | `500` entries |

> **Source:** [`src/utils/reputationCache.ts:59–62`](../src/utils/reputationCache.ts#L59-L62),
> [`src/config/env.schema.ts:279–302`](../src/config/env.schema.ts#L279-L302),
> [`src/controllers/reputation.controller.ts:93–120`](../src/controllers/reputation.controller.ts#L93-L120)

### 1.6 Idempotency records

When a write carries an `Idempotency-Key` header, the reputation idempotency
middleware stores the **complete response body** so a replay can be answered
without re-executing the write:

| Stored field | Value |
|---|---|
| `key` | `sha256(callerId:method:path:idempotencyKey)` — the raw key is never stored. |
| `payloadHash` | `sha256(stableJson(requestBody))` — the raw body is never stored. |
| `result` | `{ statusCode, body }` — the serialized response. |
| `createdAt` / `expiresAt` | Timestamps used for TTL eviction. |

For `PUT /api/v1/reputation/:id` and `POST /api/v1/reputation/:id/rate` the
stored `body` is the recomputed profile, which contains every reviewer ID and
comment for that target. For `POST /api/v1/reputation/bulk` it is the per-item
result array, where each successful item carries the created `ReputationEntry`
including its `comment`.

> **Source:** [`src/middleware/reputationIdempotency.ts:18–21, 90–119`](../src/middleware/reputationIdempotency.ts#L18-L21),
> [`src/db/idempotencyStore.ts`](../src/db/idempotencyStore.ts)

### 1.7 Audit trail entries

Every successful rating write emits a mandatory `REPUTATION_UPDATED` audit
entry. If the audit write fails the request fails with
`Failed to create audit trail. Rating not persisted.` (note: the DB row has
already been committed at that point).

Audit metadata carries `entryId`, `contextId`, `before.totalRatings`,
`after.totalRatings`, `after.rating`, and — when a comment was supplied —
`after.comment` as a **SHA-256 hash of the comment text**, never the plaintext.

> **Source:** [`src/services/reputation.service.ts:283–309`](../src/services/reputation.service.ts#L283-L309),
> [`src/services/reputation.service.ts:619–621`](../src/services/reputation.service.ts#L619-L621) — `hashComment()`

### 1.8 Webhook events and DLQ

Rating creation emits a `reputation.rating.created` webhook event on a
fire-and-forget basis — delivery failures are logged and never fail the write.
Two things are held in memory by `ReputationWebhookService`:

- **Subscriptions** — `Map<subscriptionId, ReputationWebhookSubscription>`
  containing `webhookUrl`, the HMAC `secret`, event-type filters, and an
  optional `targetFilter`.
- **DLQ entries** — after the retry ladder is exhausted, the failed delivery is
  pushed to an `InMemoryDlqStore` as
  `{ providerId, deliveryId, targetUrl, payload, timestamp, attemptCount }`,
  where `payload` is the **full event body** (`targetId`, `reviewerId`,
  `rating`, `contextId`, `entryId`, aggregate scores, and the raw `comment`).

Payloads are capped at 100 KB (`MAX_WEBHOOK_PAYLOAD_SIZE`) before delivery.

> **Source:** [`src/modules/reputation/webhook/reputation-webhook.service.ts:368–388`](../src/modules/reputation/webhook/reputation-webhook.service.ts#L368-L388),
> [`src/modules/reputation/webhook/reputation-webhook.types.ts:97–144`](../src/modules/reputation/webhook/reputation-webhook.types.ts#L97-L144),
> [`src/dlqStore.ts:131–190`](../src/dlqStore.ts#L131-L190)

### 1.9 Rate-limit counters, metrics, and logs

- **Rate-limit counters** — keyed `reputation:<auth-derived key>` with a 60 s
  default window (`RL_REPUTATION_WINDOW_MS`, 100 requests). Block records last
  up to `RL_MAX_BLOCK_MS` (default 24 h).
  *Source:* [`src/config/rateLimit.ts:301–309`](../src/config/rateLimit.ts#L301-L309)
- **Metrics** — the reputation observability middleware deliberately records
  only `operation`, `status`, `statusCode`, `errorCause`, and duration. No
  request-controlled value (user ID, comment, path parameter) is ever used as a
  metric label.
  *Source:* [`src/observability/reputation-observability.ts:26–86`](../src/observability/reputation-observability.ts#L26-L86)
- **Logs** — reputation controller logs include `freelancerId` (a user UUID) and
  the correlation ID; ratings and comments are not logged. Log retention is
  governed by the deployment's log shipping stack and is out of scope for this
  repository.

## 2. Retention Windows and Purge Behaviour

### 2.1 Ratings are append-only and retained indefinitely

`reputation_entries` rows are **retained indefinitely**. Concretely:

- There is no TTL, no expiry column, and no soft-delete window.
- There is no scheduled job, cron, or maintenance script that deletes reputation
  rows. The reputation scheduler (`ReputationSchedulerService`, daily by
  default) enqueues **recompute** jobs only — it never deletes data.
- There is no API endpoint that deletes a rating. The router exposes exactly
  four routes — `POST /api/v1/reputation/bulk`, `GET /api/v1/reputation/:id`,
  `POST /api/v1/reputation/:id/rate`, and `PUT /api/v1/reputation/:id` — and no
  `DELETE` route.
- Removing a rating therefore requires a manual
  `DELETE FROM reputation_entries WHERE …` against the database, executed
  out-of-band by an operator.

> **Source:** [`src/routes/reputation.routes.ts`](../src/routes/reputation.routes.ts),
> [`src/services/reputation-scheduler.service.ts:26–36, 122–146`](../src/services/reputation-scheduler.service.ts#L26-L36)

### 2.2 Process-lifetime stores

| Store | Window | Purge mechanism |
|---|---|---|
| `reputationStore` (profiles) | Process lifetime — no TTL, no size cap | Overwritten on the next recompute for that target; `delete(id)` / `clear()` exist but are used only by tests. Lost on restart. |
| `reputationCheckpointStore` | Process lifetime — no TTL | `deleteCheckpoint(jobId)` exists but the recompute processor never calls it; completed checkpoints stay in the map with `status: 'completed'` until restart. |
| Webhook subscriptions | Process lifetime | `removeSubscription(id)` / `clearSubscriptions()` only. |
| Webhook DLQ entries | **Unbounded** — no TTL and no size cap | Removed only when an operator calls `drainDlq(providerId, count)` (or `clearDlq()` in tests). |

Neither the profile store, the checkpoint store, nor the DLQ enforces a size
bound, so an operator running a long-lived process with a persistently failing
webhook endpoint should monitor DLQ depth (`getDlqDepth()`) and age
(`getDlqOldestAge()`) and drain it.

> **Source:** [`src/models/reputation.store.ts:40–53`](../src/models/reputation.store.ts#L40-L53),
> [`src/models/reputation-checkpoint.store.ts:121–153`](../src/models/reputation-checkpoint.store.ts#L121-L153),
> [`src/dlqStore.ts:131–190`](../src/dlqStore.ts#L131-L190)

### 2.3 TTL-bounded stores

| Store | Window | Purge mechanism |
|---|---|---|
| Read cache (`reputationCache`) | `REPUTATION_CACHE_TTL_MS`, default **60 s** | Lazy: a `get()` on an entry whose age `>= ttlMs` deletes it and reports a miss. Capacity eviction removes the LRU entry when `maxEntries` (default 500) would be exceeded. Write paths call `invalidate(targetId)` after every successful rating (including per-target in the bulk endpoint), so a post-write read never serves stale data. |
| Idempotency records | **1 hour** (`ttlMs: 60 * 60 * 1000`), capped at **10 000** records | `get()` treats an expired record as absent and deletes it; a background `setInterval` sweep (60 s, `unref`ed) calls `purgeExpired()`. |

> **Source:** [`src/utils/reputationCache.ts:136–192`](../src/utils/reputationCache.ts#L136-L192),
> [`src/middleware/reputationIdempotency.ts:18–21`](../src/middleware/reputationIdempotency.ts#L18-L21),
> [`src/db/idempotencyStore.ts:28–75`](../src/db/idempotencyStore.ts#L28-L75)

### 2.4 Audit entries

`REPUTATION_UPDATED` entries are retained **permanently**. The audit log is an
append-only, hash-chained ledger; purging any entry breaks `verifyIntegrity()`
from that point onward. There is no automated purge and no TTL. See
[audit-retention.md](./audit-retention.md).

**Consequence for erasure requests:** deleting a user's rows from
`reputation_entries` does **not** remove the corresponding audit entries. Those
entries retain the actor ID (reviewer), the resource ID (target), the numeric
rating, and the SHA-256 hash of the comment — but never the comment plaintext.

### 2.5 The automated retention engine does not cover reputation

`DataEntityType` (`src/retention/types.ts`) defines exactly six entity types:
`contract`, `user_profile`, `transaction`, `audit_log`, `document`, `message`.
There is **no** `REPUTATION` entity type.

Reputation data is therefore outside the `DataRetentionManager` lifecycle
entirely — it is never assigned an `expiresAt`, never archived by
`DataArchivalService`, and never considered by `src/retention/purge.ts`.
`RETENTION_OVERRIDES` cannot be used to set a reputation retention period.

> **Source:** [`src/retention/types.ts:63–70`](../src/retention/types.ts#L63-L70),
> [`docs/DATA_RETENTION.md`](./DATA_RETENTION.md)

## 3. PII Handling

The reputation subsystem stores no names, emails, addresses, or payment
details. What it does store falls into three buckets.

**1. User identifiers.** `reviewer_id` and `target_id` are internal user UUIDs
and `context_id` is a contract UUID. They are not PII on their own, but they are
foreign keys into `users`, so a rating is trivially linkable to a real person
holding that account.

**2. Free-text comments (the main PII risk).** `comment` accepts up to 1000
characters of arbitrary user input and **is not redacted, masked, or scanned**
anywhere in the reputation code path. Service-layer `validateComment()` enforces
length, rejects whitespace-only strings, and rejects comments where a single
character exceeds 50 % of the body — these are spam/abuse rules, not PII
controls. A reviewer who writes a name, phone number, or email into a comment
has that text stored verbatim.

Comment plaintext is reachable in these places:

| Location | Plaintext comment? |
|---|---|
| `reputation_entries.comment` (SQLite) | **Yes** — indefinitely. |
| `GET /api/v1/reputation/:id` response (any authenticated caller with `reviews.read`) | **Yes**. |
| Read cache (`reputationCache`) | **Yes** — up to the 60 s TTL. |
| Idempotency record `result.body` | **Yes** — up to 1 hour. |
| In-memory profile store (`reputationStore`) | **Yes** — for the process lifetime, after a recompute pass. |
| Outbound webhook payload / DLQ entry | **Yes** — see the note below. |
| Audit metadata (`after.comment`) | **No** — SHA-256 hash only. |
| Metrics labels | **No** — no request-controlled labels are recorded. |
| Application logs | **No** — comments are not logged. |

> **Note on webhooks:** the JSDoc on `ReputationRatingCreatedData.comment` in
> [`reputation-webhook.types.ts`](../src/modules/reputation/webhook/reputation-webhook.types.ts)
> reads *"Optional review comment (redacted if present)"*, but
> `createRatingCreatedEvent()` copies the comment through unchanged and
> `deliverToSubscription()` sends it as-is. Comment text **is** transmitted to
> every matching subscriber and is retained verbatim in the DLQ payload if
> delivery fails. Treat the comment as leaving the system boundary in
> plaintext when planning subscriber vetting or a data-processing agreement.

**3. Derived aggregates.** `score`, `weightedScore`, and `totalRatings` are
computed from ratings and expose behavioural information about a user, but no
direct identifiers beyond `freelancerId`.

Cross-cutting protections that do apply: audit entries pass through the standard
redaction pipeline (`src/audit/redact.ts` — header suppression, sensitive-key
redaction, email masking such as `alice@example.com` → `ali***@example.com`),
and the idempotency middleware stores only SHA-256 digests of the key and the
request payload rather than their plaintext.

## 4. Summary Table

| Store | What it holds | Retention window | Purge mechanism | Plaintext PII exposure |
|---|---|---|---|---|
| `reputation_entries` (SQLite) | Rating rows incl. comment | **Indefinite** | None — manual SQL only | Comment free text; user/contract UUIDs |
| Reputation profile (derived) | Aggregates + reviews | N/A — recomputed per read | N/A | Mirrors entries |
| `reputationStore` (in-memory) | Recomputed profiles | Process lifetime | Overwrite / restart | Comment free text |
| `reputationCheckpointStore` | Recompute job progress | Process lifetime | `deleteCheckpoint()` (unused) / restart | Last-processed user UUID |
| `reputationCache` (LRU) | Profiles for GET | 60 s TTL, 500 entries | Lazy TTL expiry, LRU eviction, write invalidation | Comment free text |
| Idempotency records | Response bodies | 1 h TTL, 10 000 max | Lazy expiry + 60 s sweep | Comment free text (in stored body) |
| Audit entries (`REPUTATION_UPDATED`) | Actor, target, rating, comment hash | **Permanent** | None — hash-chained ledger | None (comment hashed) |
| Webhook subscriptions | URL, HMAC secret, filters | Process lifetime | `removeSubscription()` | Signing secret |
| Webhook DLQ | Failed event payloads | **Unbounded** | Manual `drainDlq()` | Comment free text |
| Rate-limit counters | Request counts / blocks | 60 s window; blocks ≤ 24 h | Window rollover | Auth-derived key |

## 5. Operator Notes

- **There is no reputation retention policy to configure.** The only tunable
  windows are the cache TTL, the cache capacity, and the idempotency TTL — all
  performance controls, not compliance controls.
- **Erasure is manual and incomplete by design.** Deleting a user's reputation
  data requires `DELETE FROM reputation_entries WHERE target_id = ? OR
  reviewer_id = ?` plus a cache invalidation and a process restart (to clear
  `reputationStore`). The corresponding audit entries cannot be removed without
  breaking the audit hash chain.
- **Foreign keys constrain deletion order.** `reviewer_id` and `target_id`
  reference `users(id)` and `context_id` references `contracts(id)`; delete
  reputation rows before the referenced user or contract rows.
- **Watch the DLQ.** It is the one reputation store with neither a TTL nor a
  size cap that can hold comment plaintext indefinitely.
- **Feature flag.** With `REPUTATION_ENABLED=false` (the default),
  `createRating` and `getProfile` throw `403 Forbidden`, so no new reputation
  data is written — but data written while the flag was on is unaffected.
